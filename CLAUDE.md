# Sanga Admin
- Plain HTML, CSS and JavaScript. No framework. `public/` is the website; `server.js` serves only that folder.
- Same Firebase project as the Sanga app (same Firestore, same phone + PIN accounts). `public/login.html`, `public/js/firebase-config.js` and `public/js/sanga-auth.js` are copies of the app's files: keep them in step with the main sanga repo.
- Every admin page is hidden until `public/js/admin-session.js` confirms the person is logged in and has a record in the Firestore `admins` collection. Keep that pattern for any new page: lock snippet in `<head>`, then the Firebase scripts, `sanga-auth.js`, `admin-session.js`.
- Admin records are created only by a main admin (Firestore rules). Never read the `users` collection from the browser: it holds PIN hashes. Use a Cloud Function.
- `firestore.rules` and the Cloud Functions live in the MAIN sanga repo; `main-repo-changes/` holds the versions this site needs.
- `admin_review.html`'s Events review tab reads and writes real events straight from Firestore (`sanghaDb.collection('events')`, live-synced with `onSnapshot`). Its Host tab is derived from that same live event list (one row per distinct `hostId`/`hostName`, grouped the same way events are filtered) — there's no separate host-profile collection yet, so fields a real profile would have (rating, join date, suspended/active) don't exist: "events" is a real count, and "Suspended" stays empty until a real suspend feature exists. Its Messages tab has no real data behind it at all yet (no Firestore collection or Cloud Function for customer/support messages anywhere in the app) and is intentionally left empty rather than showing fabricated conversations.
- `public/event_prototypes.html` (linked from Admin Settings, left of Cover library; main admin only) publishes one event per app category ("Publish" / "Unpublish"), straight to the Firestore `sampleEvents` collection — real, not sample data. The app's `/events/sample_events.html` and `/events/create_event.html?sample=` read the same collection. Its `EVENT_CATEGORIES` constant is the app's actual event categories — a different list from `admin_settings.html`'s own `CATEGORIES`, which is this site's unrelated review-queue scope.
- Never put API keys or secrets in any file. Work on a branch and open a pull request; never push to main.
- `public/event_detail_view.html`, `js/firebase-config.js` and `js/sanga-auth.js` must stay IDENTICAL to the app repo's copies. `js/sanga-nav.js`, `js/sanga-data.js` and `login.html` share names with app files but are different on purpose: never overwrite them with the app's versions.
- Cover library: `public/cover_library.html` (linked from Admin Settings) adds and views photos for the "Suggest one" button on Create event; any admin can add, only a MAIN admin removes photos or downloads the zip. It needs Firebase Storage on, plus `main-repo-changes/storage.rules` and the `coverLibrary` block in `firestore.rules` deployed from the main repo, and the `nextCoverPhoto` function (main repo). For the zip download, apply `main-repo-changes/storage-cors.json` to the bucket once.
- Installable as a PWA (own manifest/service worker, separate from the app's): `public/manifest.webmanifest`, `public/sw.js`, `public/offline.html`, `public/js/sanga-pwa.js` (registers the worker only — no install-hint banner, unlike the app). Every page's `<head>` links the manifest, sets `apple-mobile-web-app-title` to "Sanga Admin", and loads `sanga-pwa.js` — except `event_detail_view.html`, which keeps the app's own title ("Sanga") since that file must stay identical to the app repo's copy. New pages should do the same.
